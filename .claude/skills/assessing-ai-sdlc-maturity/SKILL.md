# AI-SDLC 成熟度アセスメント

`/assessing-ai-sdlc-maturity` と明示的に指定されたときだけ動く（モデルが自発的に呼ぶことはない）。引数：第 1 引数は対象リポジトリのパス（省略時はカレント）。`再評価 #<番号>` または `再評価 <前回の証拠 JSON のパス>` が付いていれば、そのベースラインと比較できる版のシートで再採点し、差分だけを報告する。`書き込みなし` が付いていれば、対象リポジトリにも GitHub にも書き込まずに評価する（手順 2 と 6 の「書き込みなしモード」）。

## 概要

DEFRA「AI-SDLC Maturity Assessment」の 7 段階尺度（−1〜5）と階層準拠採点法を、Gigacore「AI-Maturity-Model」の 6 軸に対応づけた **固定の判定基準シート**（`criteria.md`）で、リポジトリの一次証拠（git 履歴・ファイル・GitHub の Issue / PR / Actions）から採点する。GitHub の外で回っているプロセスは証拠として拾えず低く出るので、結果はチームで話し合うためのドラフトとして扱う。基準をセッションごとに作り直すと四半期ごとの再評価で比較できなくなるので、**シートは正本として同梱し、変更は版を上げて差分を残す**。

## 手順

1. **フレームワークの差分確認**（初回、または前回の確認から 3 か月以上空いたとき。前回の確認日はベースラインの証拠 JSON の `header.framework_checked_at`）
   `curl -sL https://raw.githubusercontent.com/DEFRA/ai-sdlc-maturity-assessment/main/{README.md,introduction/ai-sdlc-maturity-assessment-framework.md,implementation/scoring-implementation.md}` と `https://raw.githubusercontent.com/Gigacore/AI-Maturity-Model/main/README.md` を取得し、尺度・採点ルール・軸が `criteria.md` 冒頭の記載と変わっていないか見る。変わっていればシートの版を上げる。次元ページの Sample assessment questions は、シートに無い項目を追加するときだけ取得する。確認した日は、手順 2 の実行で `--framework-checked-at <確認した日>` に渡す。今回確認しないときは、前回の確認日を渡す（前回も無ければ渡さずに `null` のままにし、評価の限界に「フレームワークの差分は未確認」と書く）。
2. **証拠収集スクリプトの解決と実行**
   対象リポジトリの証拠収集スクリプト（`collect-evidence.sh`）を見つけて実行し、一次証拠の JSON を得る。スクリプトはすべて読み取り専用で、`.env` には触れない。既定の集計期間（窓）は 90 日。ファイルの有無と中身は、git で追跡されているファイルだけを見る。
   - **評価するコミットの確認**：実行する前に、対象リポジトリの現在のブランチ、未コミットの変更（`git status --short`）、既定ブランチとのずれ（`git rev-list --count HEAD..origin/<既定ブランチ>`）、最後に fetch した日時を確かめる。既定ブランチの最新と違えば、そのことをユーザーに知らせ、どれを評価するかを決める。最新を評価するときは、作業ツリーに触れずに、`git fetch` のうえで `git worktree add <一時ディレクトリ> origin/<既定ブランチ>` で取り出し、そのディレクトリを対象に実行する（終わったら `git worktree remove` で片付ける）。実行後は `header.evaluated_ref` を見て、評価したブランチとコミットをレポートに書く。
   - **スクリプトの探索順序**：
     1. エージェント向け指示書（`AGENTS.md` / `CLAUDE.md` / `GEMINI.md` / `.github/copilot-instructions.md` / `.github/instructions/*.instructions.md` 等）や README に書かれた `collect-evidence.sh` のパス
     2. 標準パス（`scripts/ai-sdlc/collect-evidence.sh`、`scripts/collect-evidence.sh`、`.agents/collect-evidence.sh`）
     3. 書き込みなしモードでの再評価なら、ベースラインの証拠 JSON の `header.config` と `header.skill_version` から再生成する（下記）
   - **スクリプトが無い場合（初回実行時のスキャフォールド）**：
     1. 対象リポジトリの構成を調べる。対象は、主要言語、テストランナーとテストファイルの命名、pre-commit・タスクランナー・CI の定義、デプロイ用ワークフロー、ADR ディレクトリ、変更履歴ファイル、エージェント向けルールの変更履歴とルールファイル、設計・運用ドキュメントのディレクトリ、ラベル体系、AI エージェントのコミットの署名、AI のレビュアーと PR を作る AI エージェントのログイン。
     2. 既定値の正規表現が、このリポジトリで誤って一致しないか確かめる。特に、デプロイ系ワークフローの既定値の `release` は、リリースブランチの保護など、デプロイではないワークフローにも一致しやすい。一致したワークフローの一覧を見て、必要なら `DEPLOY_WORKFLOW_REGEX` を絞る。カバレッジ下限（JVM なら JaCoCo・Kover の設定がどのファイルにあるか）、テストファイルの命名も同様に確かめる。
     3. ユーザーに配置先のパスを確認する（既定：`scripts/ai-sdlc/collect-evidence.sh`）。対話できない実行（クラウドのセッション、CI 等）で応答が無いときは既定のパスを使い、結果の報告にそのパスを書く。
     4. 本スキルの `templates/collect-evidence.template.sh` を読み込み、設定ブロックの `{{...}}` をすべて手順 1〜2 で調べた値に置き換えてスクリプトを生成し、`chmod +x` する。該当が無い項目は空文字にすれば、スクリプト内の既定値が使われる。値の引用符の制約は設定ブロック冒頭のコメントに従う。ヘッダーの著作権・ライセンス表示（MIT）は消さない。
     5. 配置先のパスを、そのリポジトリがエージェント向けに使っている指示書（無ければ README）に 1 行記録する（例：`- AI-SDLC 成熟度アセスメントの証拠収集スクリプト: \`<指定パス>\``）。
   - **書き込みなしモード**：対象リポジトリに依頼範囲外のファイルを変更しない規約があるときや、ユーザーが書き込まないことを選んだときは、スクリプトを対象リポジトリの外（一時ディレクトリやエージェントの作業用ディレクトリ）に生成して、対象リポジトリのパスを引数に渡して実行する。指示書への記録（上記 5）はしない。設定ブロックに埋めた値は証拠 JSON の `header.config` に残るので、次回はそこから同じスクリプトを再生成できる（`header.skill_version` と同じ版のテンプレートを使う）。
   - **実行**：スクリプトを実行して出力 JSON を得る。数値は JSON の `evidence.<key>.value` から転記し、暗算や推測で埋めない。対象が Public リポジトリのとき、または JSON を公開の場所に投稿する予定があるときは、`--anonymize-authors` を付けて実行する（`header.authors_top5` と `l.pr_authors_window` の個人名が仮の名前になる）。Private リポジトリでも、名前を出してよいかユーザーに確かめる。標準エラーに既定ブランチとのずれの警告が出たら、上記「評価するコミットの確認」に戻る。
   - **取得できなかったキー**：`header.collection_errors` が空でなければ、`gh` で取得できなかったキーがある（`value` が `null`、理由は `error`）。一時的な失敗のことが多いので、まずスクリプトを再実行する。`header.gh_available` が `false` なら、`gh auth status` と対象リポジトリのリモートを確かめる。
   - **`gh` を使えない環境**：`gh` が入っていない、または認証できない環境（クラウドのセッション等）では、先に `gh` を用意できないか試す（公式のリリースからバイナリを取得し、`GH_TOKEN` で認証する等）。用意できなければ、GitHub MCP のツールか REST API（`curl` と `GH_TOKEN`）で、`null` になったキーを補完する。評価者によって値が変わらないように、`references/evidence-keys.md` の「GitHub MCP・検索 API で補完するときのクエリ」のクエリを使い、件数だけが要るキーは 1 ページ 1 件で取って `total_count` だけを読む。補完したキーには `"supplemented": true` を、スクリプトと同じものを数えられずに近い値を出したキーにはさらに `"approximation": "<方法>"` を付ける（書き方は同じファイルの「補完した値・近似した値の記録」）。補完・近似したキーの一覧は、評価の限界に書く。スクリプトは GraphQL API が使えなくても REST API で取得するので、GraphQL が遮断されていること自体は補完の理由にならない。
   - **休眠中のリポジトリ**：`header.last_commit_date` が集計期間（`header.window.start`）より前なら、集計期間の指標（`d.commits_window` 等）は 0 や `null` になる（理由は各キーの `note`）。集計期間を広げて再実行するか（`--window-days`）、そのままでよいかをユーザーに確かめ、どちらにしたかをレポートに書く。
   - **単独メンテナか**：`header.single_author` は、bot を除いたコミット著者（`.mailmap` で名寄せ後）が 1 名以下か、集計期間にマージされた PR の作成者（bot を除く）が 1 名なら `true`（根拠は `header.single_author_basis`）。`false` でも `header.authors_top5` が同じ人の別名に見えるときは、ユーザーに確かめてから `criteria.md` の N/A 注記を当てる。
3. **採点** — `criteria.md` の全項目について、レベル −1/0 は「状態の該当」、1〜5 は「基準の充足」として判定し、**1 から連続して満たした最高レベル**をスコアにする（−1 該当なら −1、1 未達なら 0）。
   - レベル 3 以上の充足には **運用の証拠**（実行回数・日付・件数・ログ）が要る。ルール・スキル・ワークフローが「存在する」だけでは 2 止まり。ワークフローは `gh run list` の conclusion（`skipped` や `action_required`（承認待ちで実行されていない）ばかりなら未運用）、検査の設定ファイル（依存方向の検査、カバレッジ下限等）はそれを呼ぶ pre-commit・タスクランナー・CI の行が要る。デプロイ以外の CI ワークフロー（テスト・lint 等）も、レベル 3 の根拠にするなら `gh run list --workflow <file> --created ">=<集計期間の開始日>" --json conclusion` で同じように確かめる。ドキュメントが「強制している」と書いていても、それは検証すべき主張であって証拠ではない。
   - **運用の証拠の強さ**：Actions の実行結果を取れない（権限が足りない、`gh` が使えない等）ときは、次の順で強い証拠を使い、どれを使ったかを項目別の「主な証拠」に書く。(1) ワークフローの実行結果（`gh run list` の conclusion）> (2) マージされた PR のステータス（検索の `status:success` / `status:failure` の件数）> (3) ワークフローの定義だけ。(1) か (2) があればレベル 3 の運用の証拠にしてよい（(2) を使ったときは、代わりの証拠であることを評価の限界に書く）。(3) だけならレベル 2 まで。
   - 0 と 1 の境界：0 の行は状態の説明で、1 の基準を満たせば 0 に該当していてもスコアは 1 以上。1 未達のときだけ 0。判断に迷う項目は、`criteria.md` の B・H にある充足例・非充足例を参考にし、境界的なら低い方を採って理由を書く。
   - `value` が `null` のキー（取得できなかったキー）を 0 として扱わない。再実行しても取得できなければ、そのキーは「未取得」と明記し、ほかの証拠で判定できない項目はスコアを保留して、評価の限界に書く。
   - 今回のアセスメント自身が生成した Issue・文書・コメントは根拠にしない（「洗い出した」を自作自演で満たさない）。
   - リポジトリ外（監視ダッシュボード、チャット、ドキュメントツール等）でしか確認できない項目は「未確認 = 未達」と明記して採点する。外部で行った活動でも、その出力（PR・ルール変更・変更履歴の記載）がリポジトリ内にあれば内部証拠として使える。チームから外部で運用していると申告があった項目は、スコアを変えずに、採点表の「外部運用」列に `申告あり` と出どころを書く（`criteria.md` の「外部運用の申告」）。
   - 適用不能な項目は N/A にし、理由を書く（単独メンテナの「他者育成」、本番環境を持たないライブラリ・GitHub Action の監視など。`criteria.md` の N/A 注記に従う）。統合や削除はしない。リポジトリの種類（本番サービス／ライブラリ・Action・CLI／データ基盤）は、構成（`action.yml`、パッケージの公開設定、デプロイ用ワークフロー、データの取り込み処理等）から判断してレポートに書き、判断が付かなければユーザーに確かめる。AI 以外の自動化（テスト・リリースの自動化等）が充実していても AI の基準を満たさない項目は、スコアはそのままにして、自動化の状況を「所見」に書く。
4. **集計** — 軸スコアは配下項目の **最小値**（中央値を括弧で併記）。全体は「全項目の中央値・平均」と「階層準拠（全項目が満たす最高レベル＝最小値）」を **両方** 出し、最小値を決めている項目名を書く。N/A の項目は集計から除き、除いた項目名を結論に併記する（軸の配下がすべて N/A ならその軸も N/A）。最小値を決めている項目のうち「外部運用」が `申告あり` のものは、その旨を結論に併記する。
5. **出力** — `templates/report.template.md` の見出しと表の形に沿って書く（四半期ごとのレポートを並べて比べられるように、見出しや列を変えない）。順に：結論（2 指標と一言）／評価の対象（リポジトリ・評価したブランチとコミット・リポジトリの種類・集計期間・判定基準シートの版）／KPI 数値／軸別サマリ／項目別（スコア・外部運用・判定基準・証拠・次レベルへのギャップ）／推奨アクション（対象項目と「現在→到達見込み」）／再評価周期／評価の限界（GitHub の外で回っているため証拠が取れなかったプロセス、補完・近似したキー、フレームワークの差分確認の有無を含める）。Markdown で出す（エージェントが HTML ページ等を出せる環境ならそれでもよい）。
6. **記録** — ベースラインの置き場所は、GitHub の親 Issue かファイルのどちらかをユーザーに選んでもらう。GitHub への書き込み（Issue の作成・コメント）は、ユーザーの確認を取ってから行う。書き込む前に、投稿先のリポジトリ（Public か Private か）、作る Issue の件数とタイトル、コメントに載せる内容（証拠 JSON を含むか、個人名が伏せてあるか）を示す。
   - **ベースライン（親 Issue）**：GitHub の親 Issue に、スコア表・根拠数値・次回再評価日・評価の限界と、`collect-evidence.sh` の出力 JSON を記録する。証拠 JSON はリポジトリ内には保存せず、親 Issue のコメントのコードブロックにだけ置く。
   - **ベースライン（ファイル）**：Issue に記録しないとき（書き込みなしモード、Issue を起票しない運用）は、証拠 JSON を `assessment-<評価日>.json`、レポートを `assessment-<評価日>.md` としてユーザーが指定した場所に保存する。書き込みなしモードでは、対象リポジトリの外に保存する。次回の再評価では、そのパスを `再評価 <パス>` で渡す。
   - **推奨アクション**：1 件ずつ Issue にする（Issue を起票しないときは、同じ内容をレポートの推奨アクションに書く）。背景の証拠・やること・受け入れ基準・昇格見込みを含め、**受け入れ基準は証拠キーで書く**（例：`c.adr_duplicates == []`、`f.smoke_steps >= 3 かつ f.deploy_runs.<workflow>.success > 0`）。
   - **再評価**：前回の証拠 JSON（親 Issue のコメント、またはファイル）と今回の JSON の diff を取り、値が変わったキーを列挙してから、採点の変化を説明する。表には変わった項目だけを載せる。記録先は前回と同じ（親 Issue ならコメントで追記、ファイルなら新しい日付のファイル）。`header.skill_version` が前回と違うときは、収集方法の変更で値が動いたキーがないかをリポジトリの CHANGELOG（末尾のリンク）で確かめ、採点の変化とは分けて書く。
   - **校正**：同じ HEAD に対する 2 回目以降の採点は「校正」として扱う。新しいベースラインは作らず、差分のあった項目と新しい根拠数値だけを追記する。

## クイックリファレンス

| 場面 | すること |
| --- | --- |
| 尺度・軸を決める | `criteria.md` をそのまま使う。作り直さない |
| 初回実行 | リポジトリ構成を調べ、テンプレートからプロジェクト固有の `collect-evidence.sh` を生成して、指示書か README にパスを記録（書き込みなしモードでは、リポジトリの外に生成して記録しない） |
| 評価するコミット | 実行前に既定ブランチとのずれを確かめる。最新を評価するなら `origin/<既定ブランチ>` を一時的な worktree に取り出して実行し、`header.evaluated_ref` をレポートに書く |
| 数値の根拠 | プロジェクト固有の `collect-evidence.sh` の出力 JSON（`evidence.<key>.value`）。取得件数の上限（`--limit`/`-L`）は同じキーの `limit` フィールドに入っている |
| `gh` が使えない | `references/evidence-keys.md` のクエリで補完し、`supplemented` / `approximation` を付ける |
| 改善 Issue の受け入れ基準 | 証拠キーで書く（例：`c.adr_duplicates == []`）。アセスメントと改善 Issue を同じ語彙で計測する |
| AI 関与率 | AI エージェントの `Co-authored-by` を持つコミットの割合は **下限値** と明記（トレーラー無しコミットの由来は判別不能）。歴史の長いリポジトリでは、全履歴の `k.coauthored_ratio_lower_bound` ではなく窓内の `k.coauthored_ratio_window` を主に使う |
| 全体スコア | 中央値と階層準拠（最小値）を併記。平均だけで語らない |
| 推奨の優先順 | 最小値を決めている項目 → 次に低い項目 → 昇格が 1 手で済む項目 |
| 既存の評価と食い違った | 運用証拠（`gh run list` の結果等）を添えて差分表にする。証拠が強い方を採る |
| 再評価 | 四半期ごと。優先項目は月次。前回と major・minor が同じ版のシートで行い、変わった項目だけ報告する（patch だけの違いは比較できる） |
| レポートの形 | `templates/report.template.md` |
| 証拠キーの意味 | `references/evidence-keys.md` |

## よくある間違い

| 間違い | 直し方 |
| --- | --- |
| DEFRA の次元ページを 1〜2 枚だけ読んで残りの基準を自作する | シートを使う。自作した基準は再評価で比較できない |
| どのリポジトリにも同じ固定スクリプトを使って証拠を集める | 初回スキャフォールドで、そのリポジトリの技術スタック（言語・テスト・CI 等）に合わせたスクリプトを生成する |
| 既定ブランチから遅れたローカルのチェックアウトで、そのまま評価する | 最近追加された指示書・ワークフローが欠ける。`header.evaluated_ref.behind_default` と標準エラーの警告を見て、最新を評価するなら `origin/<既定ブランチ>` を別の worktree に取り出す |
| スコアが違う 2 次元を 1 行に統合する（例：AI リテラシー 3 + 価値計測 2 → 2） | 統合しない。低い方の原因が見えなくなる |
| スキルやワークフローの存在をレベル 3〜4 の証拠にする | 存在は 2 まで。3 以上は実行の痕跡（`gh run list` の成功件数・日付）を示す。`skipped` や `action_required` ばかりなら未運用 |
| 本番環境を持たないライブラリや GitHub Action で、G・H・M を 0 と採点して最小値に入れる | `criteria.md` のリポジトリの種類ごとの N/A 注記に従って N/A にし、集計から除く |
| 外部で運用していると聞いた工程のスコアを上げる | スコアは変えず、「外部運用」列に `申告あり` と出どころを書く |
| AGENTS.md や README の「〜で強制している」を証拠として転記する | 実際にそれを呼ぶ pre-commit・タスクランナー・CI の行を grep する。無ければ 2 |
| 作業ツリーの未追跡ファイル等、成熟度と無関係な観察を軸に混ぜる | 「所見」節に分け、採点に入れない（スクリプトは追跡されているファイルだけを見る） |
| 単純平均だけを総合スコアにする | 最小値の項目が運用リスクそのもの。併記する |
| 評価結果をチャットにだけ残す | 親 Issue かファイルに記録しないと次回の比較対象が消える（どちらに記録するかはユーザーに確認する） |
| 確認なしに Issue を作る・個人名入りの JSON を公開の Issue に貼る | 書き込む前に投稿先と内容を示して確認を取る。Public リポジトリでは `--anonymize-authors` を付けて収集する |
| 出力を確定した評価として扱う | GitHub の外（口頭の合意、別ツールの記録）で回っているプロセスは低く出る。「評価の限界」に書き、チームで話し合うためのドラフトとして渡す |
| `value: null` のキーを 0 とみなして採点する | `null` は「取得できなかった」であって「0 件」ではない。`header.collection_errors` を見て再実行し、それでも取れなければ「未取得」と書く |
| GitHub MCP の検索結果を全件取得して数える | 件数だけが要るキーは 1 ページ 1 件で取り、`total_count` を読む。クエリは `references/evidence-keys.md` のものを使う |
